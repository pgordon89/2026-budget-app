# Fiscus

An AI-native personal finance platform. **Deterministic where money is involved, probabilistic where judgement is.**

Most "AI budgeting" apps are a chat box bolted onto a ledger. This one treats categorization as a measurable ML systems problem, keeps the language model away from arithmetic entirely, and gates every merge on an accuracy regression suite.

> **Status:** in active development. **Phases 1 and 2 complete**, Phase 3 underway — four-tier categorization pipeline, scored eval harness, CI accuracy gate, and a Postgres ledger with a measured correction loop. 90.8% of holdout transactions resolved at 99.4% precision for $0.48 per 1,000.

---

## The design thesis

A language model should never be the thing that decides what your account balance is. It should be the thing that decides what a transaction *means* — and even then, only after the cheap deterministic paths have failed.

Three rules the codebase holds to:

1. **The model queries; code computes.** Natural-language questions are compiled into a validated, read-only query. The result set is computed by the database. The model only narrates numbers it did not produce.
2. **Escalate, don't default.** Categorization runs through four tiers of increasing cost, and the tier that answered is recorded on every prediction. 85.7% of holdout transactions are resolved before any model is involved at all, and 90.8% end up categorized at 99.4% precision for $0.48 per 1,000 — measured, below. A tier that is not confident escalates rather than guessing.
3. **If it isn't measured, it isn't done.** Every AI-facing behaviour has a labeled fixture set and a scored eval. Accuracy claims in this README are generated by `npm run eval`, not asserted by hand.

## Categorization pipeline

The core problem: a bank hands you `SQ *BLUE BOTTLE #4432 SANFRAN CA` and you need `food.coffee`, reliably, across 54 categories, for pennies.

```
raw descriptor
      │
      ▼
  normalize ─────────────────────────────► deterministic, ~0ms
      │                                     strip processor prefixes, store numbers,
      │                                     city/state blobs, reference blobs
      ▼
  merchant memory ───────────────────────► exact hash lookup, ~0ms
      │  miss                               user's own confirmed history
      ▼
  embedding kNN ─────────────────────────► pgvector, ~10ms
      │  low confidence                     nearest labeled neighbours
      ▼
  LLM (few-shot from neighbours) ────────► structured output + schema validation
      │
      ▼
  confidence gate ───────────────────────► below threshold → user review queue
      │
      ▼
  user correction ───────────────────────► writes back to memory + embedding store
                                            (the system gets cheaper as it is used)
```

Every layer is independently measurable: hit rate, accuracy, latency, and cost per 1,000 transactions.

### Measured so far

All four tiers are built and scored on the temporal holdout. Every number below reproduces from a clean checkout with no API key and no network — the model tier replays a committed response cache, so the eval is free to run and identical every time.

```bash
npm run analyze:normalizer   # Tier 0
npm run analyze:memory       # Tier 1
npm run analyze:knn          # Tier 2
npm run analyze:llm          # Tier 3 — replays a committed response cache, no API key needed
npm run analyze:gate         # selects Tier 1's two gates against a replay with write-back
npm run analyze:learning     # what the correction loop is actually worth
```

**Tier 0 — descriptor normalization.** 2,370 distinct raw descriptors collapse onto 602 merchant keys (3.9×), with **0 collisions** — no key maps to more than one merchant. Collisions are measured separately from accuracy on purpose: a collision does not cause a miss, it causes a confident wrong answer, and it is invisible in an aggregate score.

**Tier 1 — merchant memory.** Exact key lookup against the user's own labeled history, with an abstention gate:

| | coverage | precision | resolved |
|---|---|---|---|
| Ungated plurality (baseline) | 87.6% | 96.2% | 84.3% |
| **Gated** — Wilson ≥ 0.30 *and* agreement ≥ 0.80 | **79.4%** | **99.5%** | **79.0%** |

Transfers misclassified as spend: **0 of 67**. That error class gets its own counter because it is the most expensive one in the product — a transfer scored as spending corrupts every report downstream of it, and it is invisible in an overall accuracy number.

Three things worth defending in that table:

**Two gates, because one number cannot do both jobs.** Confidence is a Wilson lower bound rather than a raw ratio, so a merchant seen exactly once scores ~0.06 instead of 100%. But Wilson moves with agreement *and* sample size, which means it scores "seen 4 times, always groceries" identically to "seen 100 times, groceries 39% of the time" — and shipping for two commits with only that gate meant Tier 1 was, on well-observed merchants, running a 39%-precision policy without anyone noticing. Agreement is now gated separately: it is the point estimate of *how often will this be right*, where Wilson is *how sure am I of that estimate*. The full account, including two wrong hypotheses discarded on measurement, is [below](#does-it-actually-get-cheaper-as-it-is-used).

**The gates are selected on a validation split, not on the holdout.** History is split again and the golden set is scored once, at settings already fixed. Picking a threshold by reading the test set produces an accuracy that estimates nothing. Selection also happens on a replay with corrections *writing back*, because that is the population a deployed store actually has — choosing against a static store is what produced the 39%-precision policy above.

**Abstention is the feature.** Trading coverage for precision is only obviously correct because the costs are asymmetric: an escalation costs a fraction of a cent at the next tier and is recoverable, a wrong answer is silent and lands in a budget total. The selection rule is stated in the script as *maximise coverage subject to a 97% precision floor*, so the trade is a policy rather than a preference.

**Tier 2 — nearest-neighbour vote.** For merchants history has never seen: find the labelled merchant keys that look most like the query and let them vote in proportion to how near they are. Scored only on Tier 1's escalations, which is the only traffic it ever sees.

| | coverage | precision |
|---|---|---|
| Of Tier 1's 272 escalations | 33.1% | 98.9% |
| — unseen merchant (177) | 41.8% | 98.6% |
| — known but ambiguous (95) | 16.8% | 100.0% |

That asymmetry is the tier working as intended: it recovers unfamiliar merchants, and mostly declines the ones the exact-match tier already found genuinely ambiguous. If an exact key could not settle `AMZN MKTP US`, a lexical neighbourhood was never going to.

**The cascade so far:**

| | coverage | precision | resolved | → LLM |
|---|---|---|---|---|
| Tier 0+1 | 79.4% | 99.5% | 79.0% | 20.6% |
| Tier 0+1+2 | **85.7%** | **99.4%** | **85.2%** | **14.3%** |

Coverage up 6.3 points with precision holding, and a third of the model tier's future bill removed. Transfers misclassified as spend: still 0.

Two things to flag honestly about this tier:

**No hosted embedding model is wired up yet.** The vectors come from a fitted TF-IDF over word and character-trigram features — offline, deterministic, zero cost, no API key. That is a deliberate ordering, not a shortcut: a hosted embedding model is a recurring bill and an availability dependency, and "embeddings would help here" stays an assumption until something measures it. This is the number a paid model has to beat to earn its place. Merchant keys are unusually friendly to lexical matching because Tier 0 already stripped the noise and what survives often names the category outright (`... COFFEE`, `... PHARMACY`, `... DENTAL`). The `Embedder` interface is the seam; swapping it changes one line.

**Its confidence is a heuristic, not a bound.** Tier 1's score is a Wilson lower bound — an actual statistical statement. Tier 2's is `agreement × nearest-similarity`, which is a defensible shape but proves nothing on its own, so it is checked by measuring observed accuracy per confidence bucket:

```
  0.10–0.20     35 txns    20.0%  ██████
  0.20–0.30     53 txns    45.3%  ██████████████
  0.30–0.40     17 txns    70.6%  █████████████████████
  0.40–0.50     77 txns    84.4%  █████████████████████████
  0.50–0.60     32 txns   100.0%  ██████████████████████████████
  0.60–1.00     58 txns    98.3%  █████████████████████████████
```

Monotone, which is the property that matters: the gate is meaningful because higher scores really are more often right. A confidence that does not track accuracy is decoration.

One more design point worth calling out: **a key is excluded from its own neighbourhood.** Without that, a merchant Tier 1 refused to answer for reappears here as its own nearest neighbour at similarity 1.0, and Tier 2 confidently repeats the answer the previous tier correctly declined to give — a pipeline routing around its own abstention.

**Tier 3 — model categorisation** (Claude Haiku 4.5). The last resort, and the only tier that costs money per transaction. Scored on the 182 holdout transactions the deterministic tiers declined:

| | coverage | precision |
|---|---|---|
| Of Tier 1+2's 182 escalations | 44.0% | 98.8% |
| — hard slice | 27.0% | 97.3% |

Transfers misclassified as spend: **0**. Latency p50 2.0s / p95 3.9s.

**The full cascade:**

| | coverage | precision | resolved | → human review |
|---|---|---|---|---|
| Tier 0+1+2 | 87.3% | 98.5% | 85.9% | 12.7% |
| **+ Tier 3** | **92.9%** | **98.5%** | **91.5%** | **7.1%** |

**What the cascade is worth, in money:**

| | cost per 1,000 transactions |
|---|---|
| Through the cascade | **$0.42** — measured |
| Every transaction sent to the model | $3.34 — extrapolated from measured mean call cost |

**87.3% of the model bill is removed by the tiers that run before it.** That is the entire architectural argument, priced.

### Three things the Tier 3 numbers actually say

**Self-reported confidence is overconfident in the middle and trustworthy at the top.** Asking a model for its own confidence is worth nothing until something checks it, so:

```
  0.50–0.70     42 txns    42.9%   ← states ~60%, right 43% of the time
  0.70–0.80     44 txns    43.2%   ← states ~75%, right 43% of the time
  0.80–0.90     15 txns    80.0%
  0.90–0.95     11 txns    90.9%
  0.95–1.00     69 txns   100.0%
```

The gate landed at 0.90 — chosen by sweep on the validation split, not by reading this table — and 0.90 is precisely where the stated confidence starts telling the truth. A pipeline that trusted the model's "0.75" would be wrong more than half the time it felt fairly sure.

**The repair loop never fired: 0 of 182 calls needed a second attempt.** That is the intended result, not a wasted feature. Forced `tool_choice` plus `strict: true` makes an out-of-taxonomy category *unrepresentable*, so the entire class of malformed-output failures is designed out rather than handled. The loop remains for what schemas can't express — strict schemas have no numeric bounds, so `confidence: 4.2` validates; and no schema can know that `income.refund` on a −$6.75 charge is wrong. Both are unit-tested. Insurance that costs nothing when unused.

**Prompt caching is declared and does nothing on this model.** The shared system prompt is ~2,900 tokens; Haiku 4.5's minimum cacheable prefix is 4,096. `cache_control` is accepted, no error is raised, and `cache_creation_input_tokens` stays 0 across all 182 calls. The floor is recorded per-model in the price table and the eval prints the cache counters, because this failure is otherwise completely silent. It is also not monotonic across model generations — a newer model is not automatically a lower floor.

## Does it actually get cheaper as it is used?

This README claimed from the first commit that user corrections write back to the merchant store, so the system gets cheaper the more it is used. `npm run analyze:learning` turns that into a measurement by replaying the 12-month holdout one transaction at a time, with a simulated user clearing the review queue, in two arms — corrections write back, or they are discarded.

The loop is worth roughly **+0.7 points of coverage and $0.045 per 1,000 transactions** in the second half. Real, and smaller than the phrase implies.

Then the interesting part. Diffing the arms transaction by transaction, the answers that existed *only because* corrections wrote back were right **64.7%** of the time — against the 97% floor everything else here is held to. The loop was buying coverage by shipping wrong answers into budget totals.

### What actually caused it

Two hypotheses were tried and discarded on measurement before the real one.

**Wrong: too little evidence.** The obvious story was that corrections create merchants known from two or three confirmations, and Wilson can't see it. So a `minSupport` floor was added and swept. It moved precision on the affected answers from 83% to 91% — never reaching target — while costing 25 points of coverage. Wrong axis.

**Wrong: the threshold was too low.** Raising Wilson from 0.30 to 0.50 moved those answers from 65% to 71%, and added 45% to the model bill. Not a fix either.

**Right: a Wilson gate is not a precision policy.** Wilson is a lower bound on a proportion, so it moves with agreement *and* sample size — and therefore scores "seen 4 times, always groceries" identically to "seen 100 times, groceries 39% of the time". The agreement a Wilson gate actually admits:

| gate | n=10 | n=30 | n=100 |
|---|---|---|---|
| 0.30 | 0.59 | 0.47 | **0.39** |
| 0.50 | 0.81 | 0.68 | 0.60 |

A 0.30 gate was never a 97%-precision policy. On well-observed merchants it is a **39%**-precision policy. It had simply never been asked, because a static seeded store has few merchants sitting near the line — and the correction loop's whole effect is to tip merchants across it.

The fix is a second gate on **agreement**, which Wilson cannot substitute for. Agreement is the point estimate of "how often will this be right"; Wilson is "how sure am I of that estimate". A mixed-basket merchant sits near 0.46 agreement at *any* sample size and is refused permanently; a small unanimous merchant passes the agreement floor and is held back by Wilson until it has been seen enough times.

Selected on a validation replay with write-back on — the population the original gate was never chosen against — the pair `minConfidence 0.30 / minAgreement 0.80` gives, on that replay: coverage 85.4%, precision 99.7%, and **100% on the marginal answers** the loop creates, versus 83% before.

End to end on the holdout, the agreement floor costs 1.5 points of coverage and 12% of the model bill, and buys:

| | before | after |
|---|---|---|
| overall precision | 98.5% | **99.4%** |
| hard-slice precision | 93.8% | **97.3%** |
| Tier 1 precision | 98.4% | **99.5%** |

Error rate on answered transactions is more than halved, 1.51% → 0.61%.

### One constraint the data could not supply

The sweep happily selects `minConfidence 0.20`, which is above Wilson(1,1) = 0.207 — meaning a merchant seen exactly **once** would answer. It scores well because this corpus's singleton merchants happen to be consistent. A single observation cannot distinguish a merchant that is always groceries from one that is groceries *this time*, so refusing n=1 is encoded as a constraint in the selection policy rather than left to the data, and the sweep then selects 0.30. Two unit tests assert the invariant directly.

### Tier 2 has the same defect, and it could not be fixed the same way

Tier 2's confidence is `agreement × nearest-similarity` — also a product, so a weak agreement can be bought back by a close neighbour. Structurally identical, and after the Tier 1 fix it accounts for most of what remains wrong.

The same treatment was attempted and **it did not work**, which is worth recording precisely because the first fix did.

`analyze:gate -- --tier=2` sweeps an agreement floor for Tier 2 on the same validation replay. That replay reports Tier 2 already at **100% precision on the answers write-back creates, with no floor at all** — there is no defect visible in it to select against. The golden replay does show one, but it is 6 to 8 answers: far too few to choose a threshold from, and choosing one by looking at the holdout would be tuning on the test set.

Taking the sweep's coverage-maximising answer anyway (`0.40 / 0.60`) was tried and measured. On the holdout it pushed Tier 2's share from 6.3% to 10.8% at 95.5% precision and dropped overall precision from 99.4% to 98.9%. Reverted.

What ships instead is the one value defensible without data: a **strict majority** (`0.51`). Below it, more of the neighbourhood disagrees with the answer than agrees — justifiable from first principles, no corpus required. It is rarely binding and changes no measured number.

So the residual stands: 13 marginal answers at 61.5% on the holdout replay, now mostly Tier 2. Closing it needs a corpus with enough Tier 2 marginal traffic to select a real threshold on, which this fixture does not produce. That is a data problem, and pretending otherwise by shipping a fitted constant would be worse than the bug.

## The eval harness and the accuracy gate

```bash
npm run eval                      # score the cascade, compare to the committed baseline
npm run eval -- --write-baseline  # accept the current numbers
```

One command scores the whole pipeline over the 1,429-transaction holdout and prints per-tier hit rate and precision, easy/hard slices, transfer misclassification, cost per 1,000, model-tier latency, and the worst confusion pairs. It writes [`evals/baseline.json`](evals/baseline.json), and on subsequent runs it diffs against that baseline and **exits non-zero on regression**.

```
                     share   precision   resolved
  tier memory         81.0%      98.4%     79.7%
  tier embedding       6.3%      98.9%      6.2%
  tier llm             5.6%      98.8%      5.5%
  human review         7.1%          —         —

OVERALL              92.9% coverage ·   98.5% precision ·   91.5% resolved
  easy slice         99.8% coverage ·  100.0% precision
  hard slice         76.2% coverage ·   93.8% precision
```

Four things about it are deliberate.

**It grades; it does not tune.** The `analyze:*` scripts sweep parameters and pick thresholds. The runner scores the already-chosen configuration and decides whether the build passes. A script that both tuned and graded would be marking its own homework, so the gates are pinned constants here rather than re-derived.

**It runs offline and free, which is why it can gate every push.** The deterministic tiers compute live; the model tier replays a committed response cache. The usual reason model evals get excluded from CI is per-run API spend — a committed cache removes it. The one job that costs money (refreshing the cache after a prompt-version change) is manual-trigger only.

**The gate is directional, per metric.** This matters more than it sounds. Loosening the memory tier's confidence gate from 0.30 to 0.20 produces:

```
improved   overall.resolvedPct:      91.46 → 93.14  (+1.68)
improved   overall.coveragePct:      92.86 → 96.22  (+3.36)
improved   cost.perThousandUsd:      0.4249 → 0.2692
REGRESSED  overall.precisionPct:     98.49 → 96.80  (-1.69)
REGRESSED  slices.hard.precisionPct: 93.75 → 88.04  (-5.71)
```

Coverage up, resolved up, cost down — three headline numbers improving. A gate watching the headline would have shipped it. It bought all of that by emitting wrong answers, and it fails on precision. Ten metrics are gated, each with its own direction; *higher* cost or *more* transfer errors are regressions, and improvements pass with a nudge to re-baseline rather than blocking.

**The tolerance is zero.** Every tier is deterministic and the model tier is replayed, so the same commit produces byte-identical numbers. That allows an exact gate instead of the usual "within a few percent" band, which is a materially stronger guarantee — a 0.1% drift is a real behaviour change, not noise.

CI ([`.github/workflows/eval.yml`](.github/workflows/eval.yml)) runs typecheck, unit tests, the accuracy gate, and a determinism check that regenerates the corpus and fails if a single byte moved — because if the fixture drifts, every accuracy number across commits is being compared against a different dataset and the gate means nothing. It runs on Node 20 and 22, and needs no secrets.

**Where the system actually fails**, from the same run:

```
  5×  shopping.household → shopping.general
  4×  personal.care      → health.pharmacy
  4×  shopping.household → health.pharmacy
```

Those are the mixed-basket merchants — a drugstore that sells both toiletries and prescriptions, a big-box retailer with no basket signal in the descriptor. This is the irreducible ambiguity the fixture was rebuilt to contain, showing up exactly where it should.

---

**Not measured:** the cost-aware routing claim. Comparing Haiku against Sonnet 5 on identical transactions needs both models reachable, and Sonnet 5 and Opus 5 both return HTTP 429 from the environment this was run in. The script reports the gap by name rather than quietly omitting it. Until that runs, "cheap model for bulk, expensive model for reasoning" is a design intention, not a result.

## Fixture corpus

No real financial data exists in this repository, and the `.gitignore` is written to keep it that way. The demo account and the eval set both come from a seeded generator.

```bash
npm run generate:data
```

Current corpus (seed `20260101`):

| | |
|---|---|
| Transactions | 3,601 over 30 months |
| History split | 2,088 (2024-02 → 2025-07) |
| Golden holdout | 1,513 (2025-08 → 2026-07) |
| Hard slice | 413 (27.3%) |
| Merchants new mid-corpus | 15 in the holdout, 6 in the validation window |
| Category coverage | 54 / 54 |
| Persona | $8,847/mo income, $8,760/mo spend, 1.0% savings rate |

Two decisions worth calling out:

**The split is temporal, not random.** The cheap tiers of the pipeline learn from the user's own labeled history. A random split would leak future labels backwards into the memory store and report an accuracy the system could never achieve in production.

**The "hard" slice is labeled explicitly.** ~30% of transactions are genuinely ambiguous from the descriptor alone — `AMZN Mktp US*2K4LM9XY3` could be household supplies or electronics; `COSTCO WHSE #0421` could be groceries or a television. Reporting one blended accuracy number over easy and hard cases hides where the system actually fails, so they are scored separately.

**Merchants churn.** The first version of this corpus had every merchant present for all 30 months, which meant *no merchant was ever new* — and Tier 2 exists specifically to answer merchants the user's history has not seen. It was being evaluated against a population that did not contain its own use case. Merchants now have lifecycles: 15 appear only in the holdout, 6 only in the validation window, and two gyms are genuine switches rather than additions. They also arrive in **near-miss families** — `PRESIDIO DENTAL` beside `PRESIDIO VETERINARY`, `MARINA MARKET` beside `MARINA DELI` — so a lexical neighbourhood is contested rather than trivially unanimous.

That change cost Tier 2 nine points of precision, which is the point: the old number was an artifact.

Amount distributions are right-skewed rather than normal. Real spend at a merchant clusters near the low end with a long tail; drawing from the midpoint of a range instead made every wide-range merchant behave like its rare expensive case and produced a fixture that spent 2× its income.
